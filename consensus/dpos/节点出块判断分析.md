// 2. 计算从创世时间到现在的时长

// 3. 计算当前slot（向下取整）

## 为什么两个节点都返回true？

### 根本原因：时间窗口边界效应

1. **节点2在slot 18182的末尾**（09:25:09.999）
   - 此时仍在slot 18182内
   - 验证者索引=2，匹配节点2地址
   - 返回true ✅

2. **节点1在slot 18183的开始**（09:25:10.002）
   - 此时已进入slot 18183
   - 验证者索引=3，匹配节点1地址
   - 返回true ✅

### 时间线分析

```
时间轴（单位：秒，相对于genesisTime）:
36364.0s  ──┐
            │ Slot 18182 (2秒窗口)
36366.0s  ──┘
            │
            │ Slot 18183 (2秒窗口)
36368.0s  ──┘

节点2检查时间: 36365.999s (在slot 18182内) → 索引2 → true
节点1检查时间: 36366.002s (在slot 18183内) → 索引3 → true
```

### 问题根源

1. **slot边界计算**：
   - slot切换发生在 `timeSinceGenesis % blockWindow == 0` 的时刻
   - 即：36364.0s, 36366.0s, 36368.0s...
   - 节点2在36365.999s（slot 18182）
   - 节点1在36366.002s（slot 18183）

2. **时间同步问题**：
   - 两个节点的时间可能略有不同步
   - 或者检查时间非常接近边界
   - 导致节点2在旧slot，节点1在新slot

3. **高频检查**：
   - 代码中每10ms检查一次（`time.Sleep(10 * time.Millisecond)`）
   - 在slot边界附近，可能连续检查跨过边界

## 解决方案建议

### 1. 增加slot边界保护
在`produceBlock`中检查`lastProducedSlot`，避免同一slot多次出块。

### 2. 精确时间同步
确保所有节点的系统时间同步，使用NTP服务。

### 3. 边界时间缓冲
在slot边界附近（如最后100ms）暂停出块检查，避免边界效应。

### 4. 日志增强
在slot切换时记录更详细的日志，包括精确的`timeSinceGenesis`和`currentSlot`计算过程。

## 总结

**节点1的计算过程**：
- 09:25:08.387-09.388: slot 18182，索引2，不匹配 → false
- 09:25:10.002: slot 18183，索引3，匹配 → **true**

**节点2的计算过程**：
- 09:25:09.999: slot 18182，索引2，匹配 → **true**

**两个节点都返回true的原因**：
- 节点2在slot 18182的末尾（36365.999s）
- 节点1在slot 18183的开始（36366.002s）
- 两者相差仅3ms，但跨越了slot边界
- 导致计算出的验证者索引不同，但都匹配各自的地址

**这是正常的边界效应**，但需要确保：
1. 每个节点在同一个slot内只出块一次（已有`lastProducedSlot`检查）
2. 时间同步准确
3. 边界处理逻辑完善
