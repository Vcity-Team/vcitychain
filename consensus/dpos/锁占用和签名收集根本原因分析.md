# 锁占用和签名收集根本原因分析

## 问题1：签名收集取消的问题

### 用户的质疑

**问题**：如果取消签名收集，谁负责出这个块？

**分析**：
- 节点2在构建区块9146时，如果发现父区块已变化（9188已同步），就取消构建
- 但如果节点2是区块9146的预期出块者，取消了就没法出了
- 实际上，其他节点可能已经在出这些区块了，或者需要跳过这些区块号

### 实际情况

从日志看：
```
09:25:06.224 - 同步区块9188 ✅
09:25:08.780 - 签名收集超时（区块9146）
09:25:09.988 - 父区块已变化，丢弃区块9146
```

**关键发现**：
- 区块9146的签名收集超时（2分钟）
- 期间同步了区块9188
- 说明：**其他节点已经在出区块9147、9148...9188了**
- 节点2的区块9146已经过时，即使完成了签名收集也无法提交（父区块已变化）

**结论**：
- 取消签名收集是**合理的**，因为区块已经过时
- 其他节点已经在出后续区块了
- 节点2应该跳过这些区块号，继续出下一个应该由它出的区块

### 但用户的质疑有道理

**问题**：如果节点2是区块9146的唯一出块者，取消了谁来出？

**分析**：
- 在DPoS系统中，每个区块号应该由特定的验证者出块
- 如果节点2是区块9146的预期出块者，但取消了，这个区块号可能永远出不了
- **这是系统设计问题**：如果一个节点因为签名收集超时而无法出块，应该怎么办？

**可能的解决方案**：
1. **超时后由下一个验证者出块**：如果区块9146的预期出块者超时，下一个验证者可以出这个区块
2. **跳过区块号**：如果区块9146无法出块，直接跳过，继续出下一个区块
3. **重试机制**：如果签名收集超时，重试构建区块，但使用新的父区块

## 问题2：锁被占用的根本原因

### 用户的指出

**关键点**：用户提到"目前底层是一个db导致这样"

### 锁占用分析

#### 代码调用链

```go
// 1. produceBlock() 获取锁
func (r *dposRuntime) produceBlock() error {
    r.lock.Lock()  // ← 获取锁
    defer r.lock.Unlock()
    
    // 2. 调用 buildBlock()
    block, err := r.buildBlock()
}

// 3. buildBlock() 构建区块
func (r *dposRuntime) buildBlock() (*types.FullBlock, error) {
    // ...
    builder, err := r.config.blockchain.NewBlockBuilder(...)
    builder.Reset()
    builder.Fill()
    
    // 4. Build() 提交状态
    block, err := builder.Build(...)
}

// 5. BlockBuilder.Build() 提交状态
func (b *BlockBuilder) Build(...) (*types.FullBlock, error) {
    // ...
    _, stateRoot, err := b.state.Commit()  // ← 同步数据库写入
    // ...
}

// 6. Transition.Commit() 提交状态
func (t *Transition) Commit() (Snapshot, types.Hash, error) {
    objs, err := t.state.Commit(...)
    s2, root, err := t.snap.Commit(objs)  // ← 同步数据库写入
}

// 7. Snapshot.Commit() 写入数据库
func (s *Snapshot) Commit(objs []*state.Object) (state.Snapshot, []byte, error) {
    // ...
    // Write all the entries to db
    if err := batch.Write(); err != nil {  // ← 同步数据库写入，阻塞！
        return nil, types.ZeroHash[:], fmt.Errorf("snapshot commit db write error: %w", err)
    }
    // ...
}
```

#### 关键问题

**数据库写入是同步的**：
- `batch.Write()`是同步操作，会阻塞直到数据库写入完成
- 如果数据库IO慢，整个`buildBlock()`流程都会被阻塞
- 锁`r.lock`一直被占用，无法释放

**签名收集也在锁内**：
- `buildBlock()`中调用`collectValidatorSignatures()`
- 签名收集超时2分钟，期间锁一直被占用
- 即使同步了新区块，也无法检查出块（因为锁被占用）

### 根本原因

**锁的粒度太大**：
- `produceBlock()`在函数开始就获取锁
- 整个构建区块、签名收集、数据库写入都在锁内
- 任何一个环节慢，都会阻塞整个流程

**数据库操作同步阻塞**：
- 状态提交（`state.Commit()`）是同步的数据库写入
- 如果数据库IO慢，会阻塞整个流程
- 签名收集期间，数据库操作可能也在进行

## 解决方案

### 方案1：缩小锁的粒度（推荐）

**思路**：将锁的粒度缩小，只保护关键状态，不保护整个构建流程

**实现**：
```go
func (r *dposRuntime) produceBlock() error {
    // 1. 快速检查（无锁）
    if r.config.blockScheduler != nil {
        // ... slot检查
    }
    
    // 2. 获取当前区块（无锁）
    currentBlock := r.config.blockchain.CurrentHeader()
    
    // 3. 检查是否应该出块（无锁）
    if currentBlock.Number >= nextBlockNumber {
        return nil
    }
    
    // 4. 构建区块（无锁，但需要保护关键状态）
    block, err := r.buildBlockWithoutLock()
    
    // 5. 更新状态（需要锁）
    r.lock.Lock()
    r.lastProducedSlot = currentSlot
    r.lock.Unlock()
    
    // 6. 提交区块（可能需要锁，取决于blockchain的实现）
    return r.submitBlock(block)
}
```

**优点**：
- 锁只在更新状态时使用，时间很短
- 构建区块、签名收集不占用锁
- 可以同时进行多个区块的构建（虽然最终只会提交一个）

**缺点**：
- 需要重构代码
- 需要确保状态一致性

### 方案2：异步签名收集

**思路**：将签名收集改为完全异步，不阻塞`buildBlock()`

**实现**：
```go
func (r *dposRuntime) buildBlock() (*types.FullBlock, error) {
    // 1. 构建区块（不等待签名）
    block := r.buildBlockWithoutSignatures()
    
    // 2. 异步收集签名
    sigCh := make(chan *SignatureResult, 1)
    go r.collectSignaturesAsync(block, sigCh)
    
    // 3. 立即返回（不等待签名）
    return block, nil
}

// 在另一个goroutine中等待签名
func (r *dposRuntime) waitForSignaturesAndSubmit(block *types.FullBlock, sigCh <-chan *SignatureResult) {
    result := <-sigCh
    if result.err != nil {
        // 签名收集失败，丢弃区块
        return
    }
    
    // 添加签名到区块
    block.ExtraData = r.addSignaturesToExtraData(block, result.signatures)
    
    // 提交区块
    r.submitBlock(block)
}
```

**优点**：
- 不阻塞出块检查
- 可以同时构建多个区块
- 签名收集失败不影响下一次出块

**缺点**：
- 复杂度高
- 需要处理区块过时的情况
- 需要确保区块提交的顺序

### 方案3：数据库写入异步化

**思路**：将数据库写入改为异步，不阻塞构建流程

**实现**：
```go
func (b *BlockBuilder) Build(...) (*types.FullBlock, error) {
    // 1. 计算状态根（不写入数据库）
    stateRoot, err := b.state.CommitWithoutWrite()
    
    // 2. 构建区块
    block := consensus.BuildBlock(...)
    
    // 3. 异步写入数据库
    go b.writeStateToDatabaseAsync(stateRoot)
    
    return &types.FullBlock{Block: block, ...}, nil
}
```

**优点**：
- 不阻塞构建流程
- 可以快速返回区块

**缺点**：
- 需要确保数据库写入的可靠性
- 如果写入失败，需要处理
- 可能影响状态一致性

### 方案4：使用读写锁

**思路**：使用读写锁，读操作不阻塞，写操作才需要独占锁

**实现**：
```go
// 在dposRuntime结构体中
type dposRuntime struct {
    lock sync.RWMutex  // 改为读写锁
    // ...
}

// 出块检查（读锁）
func (r *dposRuntime) shouldProduceBlockNow() bool {
    r.lock.RLock()  // 读锁
    defer r.lock.RUnlock()
    
    // 检查逻辑
}

// 出块（写锁）
func (r *dposRuntime) produceBlock() error {
    r.lock.Lock()  // 写锁
    defer r.lock.Unlock()
    
    // 出块逻辑
}
```

**优点**：
- 多个读操作可以并发
- 只有写操作才需要独占锁

**缺点**：
- 如果写操作频繁，效果不明显
- 需要确保读写锁的正确使用

## 推荐方案：方案1 + 方案4

### 方案1：缩小锁的粒度

**关键点**：
- 只保护关键状态（如`lastProducedSlot`）
- 构建区块、签名收集不占用锁
- 提交区块时才需要锁

### 方案4：使用读写锁

**关键点**：
- 出块检查使用读锁
- 出块使用写锁
- 多个节点可以同时检查出块

### 组合效果

1. **出块检查不阻塞**：使用读锁，多个节点可以同时检查
2. **构建区块不阻塞**：不占用锁，可以快速构建
3. **签名收集不阻塞**：不占用锁，可以异步收集
4. **状态更新需要锁**：只在更新`lastProducedSlot`时需要写锁，时间很短

## 总结

### 根本原因

1. **锁的粒度太大**：整个构建流程都在锁内
2. **数据库写入同步阻塞**：`batch.Write()`是同步操作
3. **签名收集阻塞**：2分钟超时期间，锁一直被占用

### 解决方案

1. **缩小锁的粒度**：只保护关键状态
2. **使用读写锁**：读操作不阻塞
3. **异步签名收集**：不阻塞构建流程（可选）
4. **异步数据库写入**：不阻塞构建流程（可选，需要谨慎）

### 关键点

- **不要取消签名收集**，因为区块可能已经过时
- **缩小锁的粒度**，让出块检查不阻塞
- **数据库写入异步化**，减少阻塞时间
